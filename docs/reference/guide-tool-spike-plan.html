Guide Tool — Spike Plan

Phase 0: Validate the data pipeline before building the app

March 2026  ·  Solo dev + AI agents  ·  Windows / RTX 5080

The one question this spike answers: If you record a workflow with ffmpeg, capture click timestamps with a lightweight Python listener, and transcribe with Whisper — does the combined data produce a guide that's actually useful, with reasonable frames selected at reasonable moments? If yes, build the app. If no, figure out why and fix the data pipeline before writing a single line of Tauri.
Where this comes from: An earlier plan (PLAN.md) explored a Playwright-based approach — browser automation scripts that capture selectors, network calls, and technical metadata alongside a recording. That approach works for browser-only workflows and is still worth revisiting for a "technical sidecar" layer (see the product concept). The current spike takes a more general path: OS-level capture that works across all applications, not just browsers. The Playwright idea lives on as a future add-on for web workflows that need CSS selector and API call documentation.

The spike uses gdigrab (GDI screen capture) not DXGI. GDI is simpler to set up and sufficient for validating frame quality — it will miss hardware-rendered frames on some GPU-accelerated apps. That's known and acceptable for the spike. DXGI is the right call for the full app; we just don't need it to answer the spike's question.

Build Sequence

Script 1 — record.py: Capture screen + click events simultaneously

Run two things in parallel: ffmpeg (screen recording) and pynput (click listener). Both start when the user presses Enter and stop when they press Enter again. Events are written to events.json with timestamps relative to recording start.

#!/usr/bin/env python3
# record.py — start/stop recording and click capture
import subprocess, json, time, threading, sys
from pathlib import Path
from pynput import mouse
from datetime import datetime

OUT = Path("spike-output/recording")
OUT.mkdir(parents=True, exist_ok=True)

events = []
start_time = None
recording = False

def on_click(x, y, button, pressed):
    if pressed and recording:
        events.append({"t": round(time.time() - start_time, 3), "x": x, "y": y})

# Start click listener in background
listener = mouse.Listener(on_click=on_click)
listener.start()

input("Press Enter to START recording...")
start_time = time.time()
recording = True
outfile = OUT / "recording.mp4"
print(f"⏺  Recording → {outfile}")

# ffmpeg: gdigrab (GDI screen capture), 30fps, H.264 CRF 18
ffmpeg = subprocess.Popen([
    "ffmpeg", "-f", "gdigrab", "-framerate", "30",
    "-i", "desktop",
    "-c:v", "libx264", "-crf", "18", "-preset", "fast",
    "-pix_fmt", "yuv420p",
    str(outfile)
], stdin=subprocess.PIPE)

input("Press Enter to STOP recording...")
recording = False
ffmpeg.stdin.write(b"q")  # graceful ffmpeg stop
ffmpeg.wait()
listener.stop()

events_file = OUT / "events.json"
events_file.write_text(json.dumps(events, indent=2))
print(f"✅ Recorded {len(events)} clicks → {events_file}")
print(f"   Now transcribe: whisper recording.mp4 --output-format json")

Transcription — use your existing Whisper tool

Run your Whisper tool on spike-output/recording/recording.mp4. Copy the output JSON into spike-output/transcript/transcript.json. The spike consumes whatever your Whisper tool produces — word-level timestamps are ideal but segment-level works too. Format: {"segments": [{"start": 0.0, "end": 3.2, "text": "..."}, ...]}.

If you have whisper.cpp installed, the command is: ./main -m models/ggml-large-v3.bin --output-json -f recording.mp4

Script 2 — extract_frames.py: Pull a frame for each click event

For every click at time T, extract the frame at T + 0.5s using ffmpeg's -ss seek. The 0.5s offset is the hypothesis: the UI has responded and rendered, but the user hasn't moved to the next action yet. This is the core assumption the spike is testing.

#!/usr/bin/env python3
# extract_frames.py — pull frames at click+0.5s from recording
import json, subprocess
from pathlib import Path

RECORDING = Path("spike-output/recording/recording.mp4")
EVENTS    = Path("spike-output/recording/events.json")
FRAMES    = Path("spike-output/frames")
FRAMES.mkdir(parents=True, exist_ok=True)

OFFSET = 0.5  # seconds after click to capture frame
events = json.loads(EVENTS.read_text())

for i, ev in enumerate(events, 1):
    t = ev["t"] + OFFSET
    out = FRAMES / f"step_{i:02d}_t{t:.1f}.jpg"
    subprocess.run([
        "ffmpeg", "-ss", str(t),
        "-i", str(RECORDING),
        "-vframes", "1",
        "-q:v", "2",  # JPEG quality 2 = very high
        "-y", str(out)
    ], capture_output=True)
    print(f"  Frame {i:02d}: click at {ev['t']:.1f}s → captured at {t:.1f}s")

print(f"\n✅ {len(events)} frames extracted → spike-output/frames/")

Script 3 — assemble.py: Generate the guide from all collected data

Combines click events + transcript + frames into an HTML guide. For each click, finds the nearest transcript segment and pairs it with the extracted frame. No AI involved — this is pure data joining on timestamps. The output reuses the proven HTML template structure from the existing guide work.

#!/usr/bin/env python3
# assemble.py — build HTML guide from events + transcript + frames
import json, base64
from pathlib import Path

EVENTS     = Path("spike-output/recording/events.json")
TRANSCRIPT = Path("spike-output/transcript/transcript.json")
FRAMES     = Path("spike-output/frames")
OUTPUT     = Path("spike-output/output/guide.html")
OUTPUT.parent.mkdir(parents=True, exist_ok=True)

events     = json.loads(EVENTS.read_text())
transcript = json.loads(TRANSCRIPT.read_text())
segments   = transcript.get("segments", transcript if isinstance(transcript, list) else [])

def nearest_segment(t):
    """Find transcript segment closest to timestamp t."""
    if not segments: return ""
    return min(segments, key=lambda s: abs(s["start"] - t))["text"].strip()

def b64(path):
    return f"data:image/jpeg;base64,{base64.b64encode(Path(path).read_bytes()).decode()}"

# Build steps: pair each click with its frame + nearest transcript text
steps = []
for i, ev in enumerate(events, 1):
    frame_files = sorted(FRAMES.glob(f"step_{i:02d}_*.jpg"))
    if not frame_files: continue
    steps.append({
        "num":     i,
        "t":       ev["t"],
        "text":    nearest_segment(ev["t"]) or f"Step {i} (no transcript)",
        "img_b64": b64(frame_files[0]),
    })

# Generate HTML (using the proven base64-embedded template)
step_html = ""
for s in steps:
    step_html += f"""
    <div class="step-card">
      <div class="step-num">Step {s['num']}</div>
      <p class="step-text">{s['text']}</p>
      <img class="screenshot" src="{s['img_b64']}" alt="Step {s['num']}">
    </div>"""

html = f"""<!DOCTYPE html><html><head><meta charset="UTF-8">
<style>
  body {{ font-family: Arial, sans-serif; max-width: 820px; margin: 40px auto; padding: 0 20px; }}
  .step-card {{ border: 1px solid #D0DFF0; border-radius: 8px; padding: 18px 20px; margin: 0 0 20px; }}
  .step-num  {{ font-size: 12px; font-weight: 700; color: #888; text-transform: uppercase; margin: 0 0 6px; }}
  .step-text {{ font-size: 14px; color: #222; margin: 0 0 14px; }}
  .screenshot {{ max-width: 100%; border: 1px solid #ddd; border-radius: 4px; }}
</style></head><body>
<h1>Spike Guide Output</h1>
<p style="color:#888">{len(steps)} steps · generated from events.json + transcript.json + frames/</p>
{step_html}
</body></html>"""

OUTPUT.write_text(html)
print(f"✅ Guide written → {OUTPUT}  ({len(steps)} steps)")

Review the output — manually assess quality

Open spike-output/output/guide.html in a browser. For each step, answer three questions:

  • Is the frame showing the right UI state? (Not mid-transition, not hover, not wrong screen)
  • Does the transcript text roughly describe what's happening in that frame?
  • Are the step boundaries in the right places, or are there too many / too few clicks captured?

You are the reviewer. There's no automated scoring yet — the point is to look at it with your own eyes and decide if the data pipeline is producing something worth building on.

✅ Decision Gate — Go / No-Go

Go if:

  • ≥ 70% of frames show the right UI state (the rest can be fixed with the storyboard editor in Phase 1)
  • Transcript text roughly tracks the steps (not perfectly, just directionally)
  • The output looks like a rough draft of a guide — someone unfamiliar with the workflow could follow it with some effort

No-Go if:

  • Frames are consistently wrong (hover states, mid-transitions, wrong screen entirely)
  • Transcript timing is so far off it can't be correlated to clicks at all
  • The click density is so high (every mouse move captured) that filtering is impossible

Most likely outcome: Some frames are good, some aren't. The frame picker in Phase 1 exists precisely to fix the bad ones. The spike doesn't need perfect — it needs "good enough to build on." The question is whether the good frames are good enough that a human reviewer would only need to swap maybe 20–30% of them. If it's 80%, that's a pipeline problem, not a UI problem.

What Workflow to Record First

Pick something you know well and can describe while doing it. The spike recording should be 3–8 minutes — long enough to get 15–25 click events but short enough to iterate quickly if something doesn't work.

Good spike candidates:

  • The Acme Widget Mastery badge delivery workflow — you've already done this manually, you know what the output should look like, and you have the gold standard HTML to compare against
  • Any other 5–10 step admin workflow in a tool you use regularly

Avoid for the spike:

  • Workflows with a lot of typing (typing generates many non-meaningful events)
  • Workflows that involve hover-heavy menus (hover state frames are the main thing to validate/filter)
  • Anything longer than 10 minutes (too much to review in one spike session)
Recording tip for the spike: Narrate every action clearly while you do it — "I'm clicking the Settings tab" — and pause for about 1 second after each significant action before moving the mouse. The pause gives the UI time to render before the click+0.5s frame is captured. This isn't a requirement of the system but it makes the spike frames significantly better and removes one variable from the validation.

Connection to the Playwright Plan (PLAN.md)

The earlier plan in PLAN.md described a Playwright-based approach: browser automation scripts that capture CSS selectors, network traffic, API calls, and console logs alongside a recording. That plan was oriented around technical documentation — giving developers the exact selectors and API endpoints they'd need, not just a narrative guide.

The current approach supersedes it for general recording (works across all apps, not just browsers) but the Playwright insight is still valuable as a future layer:

Captures Element name, control type, timestamp CSS selector, XPath, network calls, API responses, console logs
Good for User guides — "click the Enroll Users button" Technical docs — POST /api/enrollments → 201, button[data-testid="enroll"]
Phase Phase 1 (MVP) Phase 2+ optional layer

In Phase 2, for browser-specific workflows, both sidecars can run simultaneously. The guide output would have two views: a User Guide (clean steps for non-technical audiences) and a Technical Reference (selectors + network data for developers). That's a real differentiator that no current tool offers.

The PLAN.md also proposed auto-generating Playwright test scripts from captured workflows — this is still a valid Phase 3 idea. The sidecar event log is essentially a workflow recording; with element names from UI Automation and selectors from Playwright, you have enough data to generate a runnable test.
