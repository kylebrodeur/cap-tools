Guide Tool — Product Concept

A desktop application for recording, analyzing, and generating step-by-step admin guides

Draft — March 2026  ·  Internal

The core insight: Guidde and Scribe treat every screen state as equal — they screenshot and caption without understanding intent, narrative, or workflow structure. The result is bloated, manually-corrected guides. This tool records not just what's on screen, but what's happening — capturing OS-level events, UI element names, keyboard shortcuts, and a real-time transcript alongside the video. A local AI model then understands the workflow semantically and produces a guide that's already right the first time, with a built-in review loop for anything that needs a re-shoot.

Project Origins

This project started as a Playwright-based approach: Node.js scripts that would run browser automation, capture technical metadata (CSS selectors, network calls, API responses, console logs), and output them alongside a recording for upload to Claude Cowork. That approach was useful for browser-specific workflows and introduced the core concept of a sidecar — structured technical data captured in parallel with the video, not derived from it after the fact.

The current design generalizes this. Windows UI Automation replaces Playwright as the sidecar capture layer, making the tool work across all applications — not just browsers. But the Playwright insight survives as a future Phase 2 enhancement: for browser-specific workflows, Playwright can run as a second optional sidecar layer that captures CSS selectors and network payloads that UI Automation doesn't see, enabling a Technical Reference view alongside the standard User Guide output from the same recording session.

The other original assumption — a junior engineer running scripts, a separate Cowork session for guide assembly — is replaced entirely. This is a solo developer + AI agents project. The app is the integration point; Claude (via Cowork and MCP tools) is the AI layer running inside it, not an external manual step.

The Filmmaking Framework

The analogy that makes this product coherent: a professional production doesn't shoot once and ship. They shoot a master shot (the whole scene, wide), then go back for coverage (close-ups, inserts, reactions). The editor assembles from all of it. This is exactly the right mental model for guide creation.

Film: Master Shot
→ The Full Workflow Recording
One continuous take through the entire workflow, top to bottom. Establishes sequence, pacing, and narrative structure. Doesn't need to be perfect — it's the foundation everything else is assembled around.
Film: Coverage / Close-Ups
→ Supplemental Detail Clips
Short focused recordings of specific UI panels, tabbed settings, or complex interactions. These are the private-page-settings.mp4 equivalents — deliberate, paced, one-thing-at-a-time.
Film: Insert Shot
→ Static Screenshot of a Key Field
A clean capture of a specific UI state: a filled-in form, an activity code in the URL bar, a confirmation dialog. Sometimes a still image communicates better than a frame from a recording.
Film: B-Roll
→ Context / Navigation Screenshots
The manage dashboard, the activity list, the enrollment screen — establishing shots that orient the reader before the key action happens. Often reused across multiple guides.
Film: Re-Shoot
→ Flagged Segments for Re-Recording
After analysis, the AI flags specific steps where the recording was unclear, the UI was in a transition state, or content is missing. The user re-records just those segments — not the whole thing.
Film: Assembly Cut
→ AI-Generated Guide Draft
The first pass guide, assembled automatically from all assets. Not final, but already close. The editor (the user) reviews it and approves, annotates, or requests re-shoots — not rewriting from scratch.

Workspace 1 — Prepare

Before any recording, the user establishes the project context: what platform is being documented, who the audience is, known terminology, and a step outline. The outline is the key input — it names each step, notes expected sub-sections (e.g., "Properties panel — 5 tabs, each needs a frame"), and flags anticipated callouts. This outline becomes the HUD checklist during Capture and the structural scaffold for AI analysis in Create. A well-filled Prepare workspace means the AI arrives at Create already knowing what the guide should look like.

Workspace 2 — Capture

All recording happens here: master shots, coverage clips, and re-shoots. The built-in recorder runs ffmpeg under the hood for encoding, but uses the OS's native screen capture APIs for performance — DXGI Desktop Duplication on Windows for hardware-accelerated, zero-copy frame capture. On-screen controls are handled by the OS, not custom-built: a global hotkey set for record/pause/tag, a system tray icon for control, and an always-on-top Tauri window for the step HUD — all using native facilities. While recording, a sidecar event log captures every click, keyboard shortcut, focus change, and scroll with the target UI element name. Re-shoots triggered from Create land back here, with the app pre-loaded with the event log context for that specific step.

Workspace 3 — Create

The production workspace. After recording, the local AI model (Ollama) ingests the video, transcript, and event log and produces a proposed guide structure. The storyboard editor presents this as cards — one per step, showing the selected frame, step text, and sidecar event summary. The user reviews, approves, edits inline, picks alternative frames, and marks re-shoots. Cards flagged for re-shoot carry their full event log context back to Capture for guided re-capture. This is the loop: Create surfaces problems; Capture fixes them; Create re-analyzes and closes the card.

Workspace 4 — Publish

One-click export to HTML (self-contained, base64 images), DOCX, or PDF. Branding (logo, color scheme) is applied at export time from project defaults. Export settings: table of contents on/off, image quality, output language (future: translate via local model). LMS direct publish (Phase 3).

Stage 1 — Previz (Pre-Visualization) · Prepare

Before recording, the user sketches their outline in the app: how many steps, what sections, any anticipated "gotchas" or callout notes. This outline becomes two things: (1) a guided checklist the app shows during recording as a floating HUD, and (2) the structural scaffold the AI uses when assembling the guide. A recording with a confirmed outline going in skips the entire "figure out the structure" phase on the other side.

Stage 2 — Recording · Capture

The app records the screen using the OS native capture API (DXGI Desktop Duplication on Windows), encoding via ffmpeg with resolution/quality tuned for performance — typically 1920×1080 at CRF 18 for H.264, producing high-fidelity frames without excessive file size. On-screen recording controls use existing OS mechanisms: global hotkeys registered through the OS, a system tray icon, and a minimal always-on-top overlay for the step HUD using the app framework's native transparent window support. Simultaneously: (a) local Whisper transcription runs post-recording or in a background thread, (b) a sidecar event log records every click, keyboard shortcut, scroll, and focus-change with UI element names via Windows UI Automation. The HUD shows the current step and lets the user tag moments without interrupting flow.

Stage 3 — Analysis · Create

After recording stops, the local AI model (served via Ollama) ingests: the video, the transcript, and the sidecar event log. It produces a proposed guide structure — steps identified from the event log, screenshots selected from frames at pause-detected moments, callout notes from flagged transcript segments. It also flags segments that likely need re-shoots: low-confidence transcript, hover state detected in frame, UI mid-transition, step text ambiguous.

Stage 4 — Storyboard Editor · Create

Not a video timeline. A card-per-step interface — think a horizontal storyboard, not Premiere. Each card shows: the selected screenshot, the step text, the sidecar events for that step (e.g., "clicked Enroll Users button"), and a status badge (Good / Needs Review / Re-Shoot Flagged). The user can: approve cards, edit text inline, swap to a different frame from the same timestamp range, or mark a card for re-shoot. Coverage clips (supplemental recordings) can be dropped into the project and their frames automatically replace flagged cards.

Stage 5 — Re-Shoot Loop · Capture ← Create

For any cards flagged for re-shoot, the app doesn't just tell the user what to re-record — it already has everything needed to get them back to the exact UI state. The sidecar event log for that step is a complete record of every action taken to reach it: which menus were opened, which tabs were clicked, what navigation path was followed. The app replays that sequence automatically (using the OS accessibility API to drive actions) or step-by-steps the user through it with confirmation prompts at each action, landing them in the precise starting state for re-capture. Human confirmation is always available before actions are executed. Agent replay handles the navigation; the human handles the recording. The new footage slots in, the card updates, the guide regenerates in Create.

Stage 6 — Export · Publish

One-click export to HTML (self-contained, base64 images), DOCX, or PDF. The HTML format is already proven to work well. Export settings: include/exclude table of contents, branding (logo, color scheme), output language (future: translate via local model).

Technical Architecture Notes

Desktop Framework — Tauri + Rust + React

Decision: Tauri. Rust backend gives direct access to the Windows APIs needed (DXGI Desktop Duplication, UI Automation) without a native addon layer. The Tauri transparent frameless window handles the HUD without a custom overlay engine. React frontend keeps the UI layer familiar and fast to iterate on. No Electron — the memory overhead and process isolation don't justify themselves for a single-user local tool. Built solo + AI agents, so framework maturity and ecosystem size matter less than tight native OS access and low overhead.

Screen Capture + Encoding (Capture Workspace)

Frame acquisition uses DXGI Desktop Duplication API directly — the same path that OBS and the Windows Game Bar use. This is hardware-accelerated, zero-copy, and captures at full GPU composited output including hardware-rendered UI that GDI/BitBlt would miss. The captured frames are piped to ffmpeg for encoding. Default target: H.264 CRF 18 at 1920×1080, which produces excellent screenshot-quality frames without needing a fixed bitrate guess. For lower-powered machines, the CRF can be raised (lower quality, smaller file) or the resolution can be reduced to 1280×720 — both are configurable per project. If OBS is installed, its WebSocket API (v5) is a secondary option: the app can control OBS as the recording engine, inheriting OBS's mature scene management and hardware encoding support without reimplementing it.

On-Screen Controls (Capture Workspace)

No custom overlay control framework. Three OS-native mechanisms cover the full control surface: (1) Global hotkeys registered via the OS intercept keyboard shortcuts anywhere without window focus (Tauri's tauri-plugin-global-shortcut or Windows RegisterHotKey API from Rust). (2) System tray icon with context menu for record/pause/stop/status — zero visible chrome during recording. (3) The step HUD is a Tauri frameless window set always_on_top: true with a transparent background — minimal, draggable, outside the capture region. Total custom UI work for controls: roughly a tray menu and a small label component.

Event-Guided Re-Shoot Replay (Capture ← Create Loop)

The sidecar event log is a complete, timestamped sequence of every action taken during the recording session. When a card is flagged for re-shoot in Create, the app extracts the sub-sequence of events leading up to that step and constructs a replay plan. Replay is executed via the same Windows UI Automation API used to capture events — it can programmatically find UI elements by name and invoke them (click, focus, select) using IUIAutomationInvokePattern and related patterns. The user sees each pending action before it fires and can step through manually or approve the full sequence. This is not screen automation in the macro-recorder sense — it's targeted accessibility API calls to named UI elements, which are resilient to screen position changes and visual layout differences. After replay positions the user in the target state, the recording starts automatically and the new footage replaces the flagged frames.

Sidecar Event Capture — Minimum Viable Depth

Windows UI Automation API via Rust's windows crate. Minimum capture needed per event: element name (e.g., "Enroll Users"), control type (Button, Tab, ComboBox, etc.), and timestamp. That's it for MVP — enough for step detection, auto-drafted step text, and replay navigation. Full DOM hierarchy (parent chain, role tree) is not captured unless it's needed to disambiguate an element at replay time. Keyboard shortcut events: key + modifier + timestamp. Scroll events: direction + target element name + timestamp. No coordinates required — element names + control types give the replay system everything it needs to invoke the right target regardless of screen layout changes.

Capture scope is set in Prepare: a specific browser tab, window title, process name, or a named collection of windows. If the user doesn't specify, full-screen capture is the fallback — but the Prepare workspace will prompt: "Recording everything will make step detection noisier. Can you specify which window(s) this workflow lives in?"

Local AI — RTX 5080 · 16 GB VRAM · 32 GB RAM

Reference hardware: Lenovo with GeForce RTX 5080 (16 GB VRAM) and 32 GB system RAM. This is comfortably powerful for the workload. Two model roles:

Transcription: whisper.cpp running Whisper large-v3 directly (≈3 GB VRAM). Word-level timestamps enabled. Post-recording batch processing — no real-time constraint. On this hardware, a 10-minute recording transcribes in roughly 30–60 seconds.

Guide structuring: Qwen 2.5 14B (Q4_K_M quantization, ≈9 GB VRAM) via Ollama — fits cleanly in 16 GB alongside the OS and app, leaving headroom. Takes transcript + event log + outline, outputs structured step data as JSON. Qwen 2.5 14B outperforms Llama 3.1 8B on structured output tasks and instruction following. The model does not need to see video frames — the event log tells it what happened and the transcript tells it what was said. Guide assembly from the JSON is deterministic code, not model output. At Phase 3, if output quality needs to go higher, Qwen 2.5 32B (Q4 ≈ 20 GB, requires GPU+RAM offloading) or a Claude API call for the structuring step are both options.

Frame Selection Algorithm

The sidecar event log provides click timestamps. The best frame for a step is: click_timestamp + 0.5s — enough time for the UI to respond and render, before the user's hand has moved to the next action. Word-level transcript timestamps provide a secondary signal: last_word_of_step_spoken + 0.3s. The frame picker in the storyboard editor lets the user override either with a one-click filmstrip selection.

What Doesn't Need to Be in V1

No timeline editing, no video trimming, no transitions, no audio editing, no cloud sync, no multi-platform, no DOCX, no team features, no multi-user anything. The goal is a guide, not a production. Keep the scope tight until the solo dev loop (Prepare → Capture → Create → Publish) is fast and reliable end to end. HTML and Markdown are the only export targets that matter locally — everything else is a Phase 2+ cloud integration.

Key Differentiators vs. Guidde / Scribe

Why existing tools fail: Guidde and Scribe are fundamentally screenshot-captions tools. They capture "what was clicked" but have no model of "what was being accomplished." They can't distinguish between a navigation click (Step boundary) and a settings click (sub-action within a step). They can't detect that a five-tabbed settings panel needs five frames, not one. And they have no concept of recording quality — a mid-transition frame is used without question.
  • Semantic step understanding — Uses transcript + event log together to understand intent, not just screen changes
  • Sidecar data — UI element names from the OS mean step text is auto-drafted from actual button/label names, not guessed from screenshots
  • Pre-launch quality analysis — Flags problems before the user sees the guide draft, not after they've been confused by a bad screenshot
  • Event-guided re-shoot replay — The sidecar log is replayed to navigate the user back to the exact UI state needed for re-capture. Guidde and Scribe have no re-shoot concept at all; every correction is a full manual re-record.
  • Four clear workspaces — Prepare / Capture / Create / Publish. Each workspace has a single purpose, distinct tools, and a clear entry/exit condition. Users know exactly where they are and what they're doing.
  • Local / private — No video uploaded to a cloud service; everything runs on-device via Ollama
  • Outline-driven — The guide structure is decided before recording, not reverse-engineered from what got captured
  • Built on OS primitives — Recording controls (global hotkeys, system tray, native transparent window) use existing OS facilities. No custom overlay engine; no conflicts with the software being recorded.

Baked-In Guidance — No Cheatsheet Required

The recording best practices (narration phrasing, outline discipline, the four golden rules, the do/don't behaviors) currently live in a separate cheatsheet that the user opens on a second monitor. In the finished product, that knowledge is embedded in the experience at the right moment — through onboarding, contextual AI coaching, and pre-launch analysis. The cheatsheet becomes the source of truth for training the system, not a document the user reads.

Design principle: Every item on the recording cheatsheet should map to either (a) something the app prevents or automates away, (b) a contextual prompt that surfaces at the moment it's relevant, or (c) a pre-launch analysis flag that catches violations before the user moves to Create. If the user has to remember it, it's not in the product yet.

Decisions

Previously open questions — now closed.

App framework
Tauri + Rust + React. Direct access to DXGI and Windows UI Automation from Rust. Transparent frameless window for HUD. Small bundle. Solo developer + AI agents — no team hiring constraints.
Sidecar capture depth
Minimum viable: element name + control type + timestamp per event. No DOM hierarchy. That's sufficient for step detection, auto-drafted step text, and replay navigation. Add depth only if disambiguation requires it.
Local model
Whisper large-v3 (whisper.cpp, ~3 GB VRAM) for transcription. Qwen 2.5 14B Q4_K_M (~9 GB VRAM) via Ollama for guide structuring. Reference machine: RTX 5080 16 GB VRAM + 32 GB RAM — comfortable headroom for both models simultaneously. Scale back for lesser hardware at Phase 3.
Multi-application recording
Capture everything. Sidecar events work across all applications via Windows UI Automation — no browser-only limitation. In Prepare, the user specifies which window(s) or browser tab the workflow involves. If they skip it, full-screen capture is the fallback with a prompt to be more specific for cleaner step detection.
Acme-specific vs. general
General-purpose tool. Used by a solo developer to document any platform or workflow. Acme is one use case among many — no Acme-specific logic is baked in. The guide produced for the Widget Mastery badge workflow could equally be produced for a Salesforce process, a Figma workflow, or a custom internal tool.
Export format priority
HTML + Markdown locally, always. DOCX is not a priority — the audience doesn't need it and conversion adds complexity. Cloud publish (Google Drive, Notion) lands in Phase 2 via API integrations. HTML is self-contained and durable; Markdown keeps the text portable. Everything else is a Phase 2+ integration.
Development model
Solo developer + AI agents. No human team. Design decisions optimize for one developer iterating fast with AI assistance — not for team onboarding, distributed development, or shared codebases. Complexity budgets are tight; third-party libraries that remove surface area are preferred over custom implementations.
